How to audit Zendesk ticket tags

A tag audit is not a report on the busiest tags. It is an answer to a different question: for every tag in the instance, what is it worth, and what depends on it? Here is a method that produces an inventory you can actually act on.

Updated 30 September 2026 · ~8 min read

Why the built-in tags page is not enough for an audit

Zendesk's own Tags page shows, in its own words, "the top 100 most used tags in the last two months". That is a useful dashboard for the present — and a useless instrument for an audit, for two structural reasons:

  • The 100-tag cap. Most instances have more than 100 tags in real use, and far more in residue. An audit that stops at 100 rows by construction has already missed the long tail — which is exactly where stale, duplicate and forgotten tags live.
  • The 60-day window. A tag that was heavily used a year ago and not since is the classic deletion candidate, and it will not appear in a "last two months" view. Recency cuts out precisely the data an audit needs most.

The practical consequence: decisions made from the built-in page are decisions made from a filtered slice. The filter is reasonable for daily work and wrong for cleanup.

The metrics that matter per tag

For each tag, collect four numbers and one list. Together they separate the load-bearing tags from the residue:

  • Ticket count. How many tickets carry the tag. This tells you the blast radius of a rename or delete: renaming a tag on 4,000 tickets is a different risk profile than one on 3.
  • Closed-ticket share. The percentage of those tickets that are closed. A high count with a near-100% closed share is historical baggage — safe in principle. A high count with many open or pending tickets is live plumbing — do not touch it without understanding what it drives.
  • Last use. When a ticket last received the tag. Last use older than your longest business cycle (a quarter, or a year for seasonal support) is a strong staleness signal — but only a signal, never a verdict, because the tag may still be referenced by rules.
  • Reference list. Which triggers, automations, macros, views, SLA policies, ticket field values and organizations still use the tag. This is the one metric that determines whether "delete" is even an option. See our guide on tags referenced by triggers, views and macros.

Rule of thumb: count + last use tells you whether to consider a tag. The reference list tells you whether you may. An audit without the reference list is a shopping list, not a safety check.

Building the inventory: three sources, one table

A complete inventory needs three kinds of data from your Zendesk instance:

  1. Ticket tags at scale. The Tags API endpoint in the Zendesk API returns aggregated usage for tags (with the same kind of caps the UI has). For a full inventory you need the per-ticket picture: an export of tickets with their tag arrays. In the Zendesk App Framework this is done through the incremental ticket export, which pages through the whole history rather than a sample — that is how an app can report "every tag, every ticket" without leaving your instance.
  2. Rule definitions. Triggers, automations, macros, views and SLA policies are all available as objects with conditions. Their conditions mention tags as field conditions (for example ticket.tag is <tag>). Reading the definitions — not just the tickets — is the only way to find tags that outlive their tickets.
  3. Structural tag carriers. Ticket fields that hold tag-like values and organization tags. These are the two places people forget: a ticket field can carry a value that behaves like a tag, and an organization can carry tags that apply to all its tickets.

The output is one row per tag:

tag              count  closed  last use   used in
billing          947    88%     2026-09-29 trigger "Bill VIP first", view "Open billing"
vip-customer     1284   71%     2026-09-30 SLA "VIP response", macro "VIP greeting"
vipcustomer      31     97%     2026-09-16 —
vip customer     12     100%    2026-04-02 —
legacy-migration 240    100%    2025-11-18 —

Read the table the way an auditor reads it: the vipcustomer / vip customer rows are duplicate candidates (typo, case and separator drift), and legacy-migration looks deletable — but only if the reference column stays empty. If the same table is your source for both "what is stale" and "what is safe", cleanup decisions stop being guesswork.

What to do with the finished inventory

  • Group by intent, not by string. Tags are how agents encode meaning; duplicates are almost always the same meaning spelled differently. Cluster by meaning first (case, hyphens/underscores, spacing, obvious typos) and decide one canonical spelling per cluster.
  • Separate the three buckets. Keep (referenced or recently used), merge (duplicate of a kept tag), delete (stale and unreferenced). Anything you cannot place is "investigate", and it stays that way — do not let an uncertain row become a delete by momentum.
  • Date the snapshot. A tag inventory is a point-in-time object. Agents keep tagging; a new scan a month later can invalidate a decision. Re-scan before executing a cleanup, not just before planning it.
  • Keep the reference list with the decision. When you delete a tag, the proof that it was safe is the empty reference list at that moment. For a small team that is a sentence in a ticket; for a big cleanup it is the audit trail.

How often

Once at the start of a cleanup, then on a cadence that matches your tagging behavior: monthly for teams where agents still invent new tags freely, quarterly once a tagging convention exists. The goal of a recurring audit is not a shorter list of tags — it is a list where every tag has an owner and a reason to exist.
